# Redis Event Bus 依赖、验证与文档改进设计（2026-10-13）

## 背景与证据

本设计落实 2026-10-13 评审中接受的四项意见：独立依赖解析、可重复验证与覆盖率、双语 README 入门路径、Redis 客户端 fork 的退出路线。目标项目为 `rs-event-bus-redis` 0.7.0；设计阶段只编写文档，不改生产代码、发布包或更改远端。

- `Cargo.toml` 固定使用 `qubit-redis =0.32.7-qubit.1`，库名仍为 `redis`；接收连接通过该 fork 的 `set_max_response_bytes` 限制完整 RESP 帧（`src/client.rs`、`src/client/internal/sentinel_resolver.rs`）。取消限额会使超大响应在解码前消耗不受该配置限制的内存。
- 2026-10-13 从项目目录执行 `cargo test --lib --locked`，被受 Git 忽略的 `.cargo/config.toml` 阻断：配置尝试将包名 `redis` patch 到包名为 `qubit-redis` 的 `third_party/redis-rs`。从父目录使用 `--manifest-path` 避开该配置后，Cargo 报 `no matching package named qubit-redis found`。同日直接查询 crates.io 稀疏索引，`qubit-redis` 与 `qubit-event-bus-redis` 路径返回 HTTP 404；这是该日的发布状态证据，实施时须重新核实。
- `rs-task/Cargo.toml` 的 `[patch.crates-io] qubit-redis` 和项目内部分独立 fixture 会让本地测试使用 vendored fork，不能证明 README 所说的无 patch 安装路径。`README.md` / `README.zh_CN.md` 已说明无需 patch，措辞领先于可验证的发布状态。
- `doc/coverage-review.md` 最近一次单独记录的函数覆盖率为 516/545（94.68%），低于 95% 门槛；该报告同时声明更早的通过记录并不证明当前 HEAD 通过。本设计不把历史数字当成当前测量。
- 双语 README 的 Quick Start 只有仓库 example 运行命令及说明。双语用户指南已有可组装、可运行的完整 facade 示例，`tests/documentation/markdown_examples_tests.rs` 会检查其中的标记代码块；README 尚无同等的正文调用链验证。

## 目标与完成标准

1. **依赖可信。** 开发 checkout 能用一条明确的命令完成本地验证；对外发布后，干净的独立 Cargo 项目只凭 registry 依赖、无 `[patch.crates-io]`、无本地 path 依赖即可解析和编译 README 所列版本。发布前文档不得声称该条件已满足。
2. **验证可信。** 解决本地陈旧 Cargo 配置，给出当前源码、锁文件和 feature 集合对应的新覆盖率证据。完整 CI 的函数、行、区域门槛均通过；新增测试必须覆盖真实行为或失败边界，不为凑百分比制造镜像测试。
3. **入门可信。** 英文与中文 README 正文均提供同一场景的最小公开 API 调用链：provider 选择、编码器注册、发布、持久消费、结果检查和关闭。步骤可由现有完整示例核对，且双语语义一致。
4. **fork 可退出。** 将 `qubit-redis` fork 视为受控的临时依赖，明确上游接纳、版本发布、迁移及移除条件。任何替代实现均须在同步、异步、独立 Redis、Sentinel 和 TLS 接收路径维持响应帧限制以及超限后的 PEL 语义。

## 方案比较与选择

| 方案 | 优点 | 代价与风险 | 决策 |
| --- | --- | --- | --- |
| 先发布当前 `qubit-redis`，再向上游 `redis-rs` 合入限额能力 | 保留现有经过测试的接收语义，最短路径恢复独立安装 | 临时维护 fork；上游合入和发布不由本项目控制 | **采用，分两个里程碑** |
| 立即换成未提供同等限额的上游 `redis` | 移除 fork 快 | 超大响应可能在完整解析前占用大量内存，降低现有安全边界 | 拒绝 |
| 在 provider 内重写 RESP/TLS/连接栈 | 不受上游发布节奏制约 | 重复实现认证、TLS、Sentinel、取消与解析，回归面过大 | 当前不采用 |

两个里程碑有独立验收：**A，发布与验证恢复**；**B，上游能力可用后迁移并移除 fork**。B 的外部前置条件未满足时，A 可以完成，但不得宣称 fork 已移除。若上游明确不接受限额 API，应另起设计评估受维护的替代客户端或受限传输层；不能自动降低本设计的接收内存边界。公开 API、wire v1、消费组、重试和 settlement 行为无需为这些改进主动更改；若迁移到上游客户端确需破坏性变更，可按用户授权实施并同步迁移说明。

## 里程碑 A：依赖与验证恢复

### 包与发布顺序

`qubit-redis` 是 `qubit-event-bus-redis` 的先决包。先检查目标版本在 crates.io 的真实状态，并确认 vendored `third_party/redis-rs` 的包元数据、许可、变更和发布内容。先在本地 patch 模式完成当前源码的 CI、coverage、文档示例与 package 候选检查；这些结果只代表发布前候选。在已获单独发布授权后，按 `qubit-redis` → 索引可解析 → provider 0.7.0（或经版本核定的新版本）的顺序发布。发布完成后，再从不带 path/patch 的干净项目运行真正的 registry 安装验收。发布本身是外部不可逆操作，不包含在这次仅写文档的授权内。

在先决包尚不可从 registry 解析时，本地开发可以临时使用**包名正确**的 `qubit-redis` patch，但该配置必须显式标为本地开发用途，不能作为独立安装或发布验收证据。当前忽略的 `.cargo/config.toml` 是开发者本地状态；实施前应检查其内容和来源，修正或移除过时条目，不把私有配置文件静默提交。`ci/prepare-event-bus.sh` 与 CI 应检测同类错误，并给出明确诊断。`rs-task` 的本地 patch 只用于未发布阶段；registry 验收用独立 fixture，不能复用这个 patch。

### 验证分层

1. 本地预检：确认 `cargo metadata --locked`、当前 `Cargo.lock`、当前 Rust 工具链和被忽略的 `.cargo/config.toml` 状态。记录解析来源，阻止错误包名的 patch 混入结果。
2. 聚焦回归：先运行与覆盖率缺口对应的同步/异步故障及边界测试。新增用例应明确输入、预期 SPI 错误或恢复结果及是否发出 Redis 命令。
3. 完整门禁：运行项目 `.infra/bin/ci-check.sh` 及 coverage；保留退出码、当前 HEAD/源码标识、函数/行/区域分子分母和未覆盖函数归因。旧的封存统计只作历史记录。
4. 外部安装：发布前执行 `cargo package --list` 与 package 检查，防止 path 依赖或 vendored 开发文件泄漏为对外安装要求。provider 发布后，构造仓库外独立临时 Cargo 消费者，使用 README 的 registry 依赖版本，不提供 path/patch；依次验证 `sync+discovery`、`async+discovery` 和默认 feature。两类证据分开记录。

覆盖率优先分析 29 个未覆盖函数中的可达生产分支；先区分工具生成闭包、测试 helper 与业务路径，再补测试。若门槛通过，仍需检查相关失败语义，不以数字代替正确性。若外部依赖未发布，独立安装验收记录为“未满足”，不能以本地 patch 测试替代。

## 里程碑 A：双语文档

保留 README 的项目定位、安装、能力与限制说明；Quick Start 改为“订单事件”最小调用链。正文显示直接依赖、唯一 namespace、codec 注册、`redis-streams` 选择、`RedisSubscriptionProfile` 持久消费、发布、可观察结果和关闭。可将长的 TLS、限额、恢复策略继续留在用户指南。英文和中文按同一事实清单分别组织文字；代码符号、版本与错误边界一致。发布前将安装段落标为尚需 registry 前置包，发布验收成功后再改成直接安装说明。

对 README 新增的 Rust 块使用唯一标记，扩展现有 Markdown 示例检查来组装并编译，运行时与指南示例共享隔离 Redis fixture。文档测试不要求读者拥有源码 checkout 才能理解调用链；运行仓库 example 的命令保留为进阶验证入口。同步检查 `doc/user_guide.md` / `.zh_CN.md`、`doc/design.md` / `.zh_CN.md`、`doc/migration.md` / `.zh_CN.md` 中的包状态、限额与链接，避免一处称已发布、另一处称待发布。

## 里程碑 B：移除 fork

上游贡献须针对实际使用的公共构造路径提供 `max_response_bytes` 等价能力：在解析完整 RESP 值前限制单帧输入，限额含义、超限错误和连接失效行为可测试，并覆盖同步 parser 与异步 codec。验收需包含完整帧恰好到限、超限、分片输入、嵌套/数组响应、取消和后续连接复用，以及 provider 的 Redis 6.2/7、Sentinel、TLS 回归。上游已发布可用版本后，将 `Cargo.toml` 的 `qubit-redis` 换成上游 `redis`，调整 `src/client.rs` 与 `src/client/internal/sentinel_resolver.rs` 的构造调用、特性与锁文件，移除仓库维护的 `third_party/redis-rs` 及下游 patch，并通过独立安装验收。删除源码目录及发布操作均须在相应实施授权范围内执行；本设计文档本身不执行这些操作。

## 风险、回退与边界

- 发布顺序若反转，README 示例即使在本地通过，也会在新消费者中解析失败；发布前以独立项目的 registry 构建为硬门禁。
- 上游迁移时严禁用 `redis.max_wire_bytes` 的应用层解析检查替代 RESP 帧检查；前者发生在客户端构造响应值之后。
- 升级 Redis 客户端可能改变 TLS、Sentinel 或取消行为；必须比较错误类别、未知 XADD/XACK 结果、PEL 留存和超限停止订阅的语义。若 B 的门禁失败，回退到已验证的 `qubit-redis` 版本，保留 fork 状态并记录阻断原因。
- `rs-task` outbox 对未知发布结果可能重发相同事件 ID，业务仍须去重；本次不引入“恰好一次”承诺，也不改变 outbox 删除条件。
- 编码风格与 Rustdoc 继续由既有 style/Clippy/Rustdoc 门禁检查。本轮没有证据支持在这些方面做与目标无关的批量重构。
