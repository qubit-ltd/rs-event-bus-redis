## 当前测量口径

harness 只调用公开同步和异步 provider SPI。多个独立 worker 线程共享一个
provider；每个 worker 独占 durable receiver 和 topic，顺序完成 publish、receive、
Accept。异步 worker 使用 `futures_lite::future::block_on` 驱动运行时中立的 future，
因此数据对应这一执行器安排。预建消息、receiver、线程、Redis 启动、CSV 写入均在
计时区外。共享原始 payload 恰为 64、4,096、262,144 字节，JSON wire 元数据及字节数组
展开额外计算。起跑屏障同时释放 1、8、32 个 worker。

默认及受限命令名额配置，每个组合每轮恰有 1,000 次尝试，共三轮。受限配置将
`redis.max_concurrent_commands` 从 64 改为 32，`redis.max_idle_connections` 从 8 改为 1，
receiver 数低于默认上限 256。默认保留 8 个结算名额后，32 个总命令名额中只有 24 个
可供普通命令使用，因此并发 32 可能被拒绝；总命令限额不保证所有 worker 的命令都能
准入。业务轮次必须恰有 1,000 次成功、零错误；无效轮次保留原始证据，先排查再用全新
fixture 整轮重测，绝不通过重试单次发布填满成功样本。另有仅 after 的 command_limit 场景：并发 32、命令名额 1、idle pool 1、每轮 1,000 次尝试，
成功和拒绝分别报告，所有拒绝保留 CSV。receiver 限额场景持有唯一获准 receiver，
三轮各测量 1,000 次被拒绝的 subscribe。基线不认识新增限额配置，因此不比较此类场景。
10、100 个空闲 receiver 使用 1-ms 短 poll，Redis 调度可使实际等待明显更长。

after 的其他默认值保持：连接/命令预算各 2,000 ms，原始 payload 上限 1,048,576 bytes，
完整 wire 上限 8,388,608 bytes，最短 claim idle 30,000 ms、recovery interval 1,000 ms、
每 receiver 最多 100 个未结算 delivery。关闭 approximate stream trimming。worker 使用
durable group、`StartPosition::New`、空 headers 和 `application/octet-stream`。
基线保持自身默认行为，没有新增的命令/receiver 名额及 wire 尺寸预算。

吞吐分母为释放起跑屏障至所有 worker join 的时间，分子为成功 Accept 的事件；
idle 场景计数 TimedOut poll。使用 `Instant` 测量每次完整尝试，成功样本的 p50/p95/p99
采用 nearest-rank，失败尝试另有对应分位数。错误及未知结果依据 SPI `kind()` 分类。
每个尝试（含错误）均保存 CSV。setup 不计入延迟/吞吐，但计入新建连接和命令 delta。
固定 INFO observer 和峰值 sampler 在基线快照前连接，其建立连接不计入 delta；
活跃连接快照包含这两个 observer。峰值 sampler 在 INFO 响应之间等待 5 ms，实际间隔
还包括命令时间及调度等待，可能遗漏更短的峰值。
XAUTOCLAIM/XREADGROUP 使用 Redis INFO commandstats 累计值之差，零值亦记录。

独立 standalone fixture 优先用本地 `redis-server`，否则用 Docker `redis:7-alpine`；
配置 loopback、AOF、`appendfsync everysec`。每个场景只清空 benchmark 自己拥有的库；
外部 URL 绝不清空。每轮 Sentinel 新建 master、replica、三个 Sentinel。先测量 1,000 次
发布，观察复制追平作为 fixture setup 条件，再强制停止 master，等待两个 Sentinel
投票及 replica `INFO replication` master-role 收敛，通过同一个 provider/client 实例及 receiver 重试。恢复 elapsed 包含
停止、晋升、错误、重试等待和首次 Accept；单次恢复尝试延迟另计。发布获得 ACK 后仅重试 receive 并核对同一个 event ID；
发布错误（含未知结果）及结算错误立即停止，不重放该事件。receive 未知结果计入原始
数据，并依恢复合同再次调用同一 receiver。随后测量 1,000 次
恢复后事件。不使用 observer WAIT 充当 provider 写复制 fence 或持久性保证。
恢复成功样本的延迟只覆盖已获 ACK 后的 receive/Accept，发布失败样本只覆盖该 publish；
完整 failover 延迟另取三轮 recovery elapsed。恢复连接/命令 delta 只观察晋升后的 replica，
故障前观察原 master。Sentinel 计数包含控制面/复制连接；fixture 查询在故障前复制检查
期间复用基线快照前的 observer。晋升会主动关闭普通客户端连接
（[Redis 7.4.8 实现](https://github.com/redis/redis/blob/7.4.8/src/sentinel.c#L4501)）。
至少两个 Sentinel 投票后，仅 fixture observer 的 I/O 错误触发连接同一晋升 endpoint 并
重新确认 master role；晋升后 peak sampler 亦重开。恢复连接 delta 包含这两次 observer
新建连接。恢复峰值取两个区间真实采样的最大值；promotion 期间存在采样空隙，因此只是
观测下界，不是真实最大值。其他场景保持一个 sampler。

```sh
REDIS_BENCH_LABEL=after \

```

`REDIS_BENCH_SAMPLES` 默认 1,000，`REDIS_BENCH_ROUNDS` 默认 3；
每次使用新 label 或空输出目录，原始 CSV 绝不覆盖。
`REDIS_BENCH_FIRST_ROUND` 默认 1，用于标识分别配对的轮次。可选专用
`REDIS_BENCH_URL`。诊断筛选变量为 `REDIS_BENCH_MODES`、`REDIS_BENCH_SCENARIOS`、
`REDIS_BENCH_LIMITS`、`REDIS_BENCH_PAYLOADS`、`REDIS_BENCH_CONCURRENCY`，均使用逗号
分隔列表。筛选或缩小样本必须披露，不能替代完整矩阵。场景为 `round_trip`、`idle`、
`command_limit`、`receiver_limit`、`sentinel`。外部 driver 将同一份公开 API 源码指向清洁基线，不改基线
生产行为。Sentinel 异步访问每次连接重新解析 master；该场景验证同一 provider/client
实例恢复，不声称验证 Sentinel master socket 缓存失效。standalone 缓存复用单独测量。
前后两次都隔离其他 Redis 负载。机器为共享工作站，可比 default 场景按每个配置、
每轮 before→after 交错配对，记录时间戳、load/CPU 快照。主要吞吐每次最多等待后台
编译 30 秒，超时继续测量并为该轮记录编译/load 扰动。稳定疑似退化先核对配对负载，
恢复后的 bounded runner 累计等待编译预算为五分钟；预算耗尽后保留环境标记并直接继续。
不同噪声下重测。后续安静窗口等待总预算为两分钟；若仍没有窗口，则明确无法判定
稳定性能归因。高负荷诊断数据不用于最终退化结论。

### 实际行为与解释

此基线已经具有连接复用。concurrency 1 的所有 default 业务轮两侧均新增
两个被测连接、采样四个 active client；十个 idle receiver 两侧均新增 11 个
连接，包含 receiver setup。因此本轮没有复现历史较早基线的 99.66% 降幅。
高并发连接 churn/peak 有波动，完整数字保留如下，不能把 admission cap
解释为 Redis client 总数上限。

100 个 idle receiver 中，after sync 三轮有 929/860/835 次 timed-out poll
及 71/140/165 次 `receive:resource_limit`；async 为 815/889/816 次 poll
及 185/111/184 次拒绝。before 每轮 1,000 次 timed-out poll、零错误。
100 receiver 符合独立的 256 receiver cap，但同时执行恢复命令可能超过默认
64 个 command 名额。这些错误均无 unknown。after 连接 churn 最大 283，
采样 active peak 最大 184。command admission 并非全部物理 Redis client
上限：reader、idle connection、observer、控制连接各有生命周期。idle
吞吐成功分子少于 1,000，分母仍为 elapsed time，不能宣称为无条件性能提升。

command 名额为一时，sync 三轮仅成功 38/2/17、async 31/9/21，每轮分母
1,000 attempts。拒绝发生在 publish、receive 或 settle，没有 unknown 或自动
重放。单 receiver 场景每轮 1,000 subscribe 全部拒绝，未发送 Redis 命令
（new connections、XAUTOCLAIM、XREADGROUP 均为零）。32 command/one-idle
的 limited 主矩阵独立达到每配置每轮 1,000 成功，不代表一名额配置可全成功。

每个 Sentinel 业务 phase 完成 1,000 events、零错误。业务及 receiver setup
命令后采样 master 目标 offset，再确认 replica offset 不低于该目标。所有
fresh 成功轮均记录至少两票晋升及 master role 收敛。完整恢复耗时 before
2.325–2.639 秒、after 2.354–2.687 秒。after 每轮计一次 receive unknown
之后接受原先已确认 publish 的 event；before 没有 unknown。恢复连接 delta
包含两个 fixture observer 重开，promotion 采样间隙使两段 peak 最大值仅为
下界。这验证相同 provider/client instance 的故障恢复，不构成 provider
写复制保证，也不验证 cached async Sentinel socket 失效。

### 保留失败与共享主机局限

最初 before sync Sentinel 轮完成 1,000 pre-failure events 和复制检查后，
replica observer 在晋升期间 EOF。独立 fresh fixture 重现中旧 normal-client
observer 断开，而新 observer 确认 master role。V2 helper 仅在 quorum votes
和 I/O 错误后，在原 deadline 内重开同一 endpoint，保留 role/offset 屏障。
随后 before/after 所有 Sentinel 轮均 fresh 实测。失败 raw 排除于 accepted
总数。

一个 after async limited、262,144 字节/concurrency 8 的轮次只有 966 成功、
34 错误：settle unknown 2.019563687 秒、publish unknown 2.007222953 秒、
32 个 event-ID mismatch。全部 mismatch 为 worker 5 sequence 93–124，
紧接该 worker sequence 92 的 unknown publish；这支持 stream cursor 级联
假说，但没有记录返回实际 ID 或错误后 Redis 状态，不能证实 XADD 已应用。
这些错误不是 ResourceLimit。该 invocation 的 host I/O-wait ticks 为 38.55%，
load 14.06→14.69，端点均观察到外部编译器。快照包括 fixture 启停和业务
阶段，因此主机争用只是候选原因，未确认根因。仅一次整轮 fresh fixture
重测，timeout/config 均未变，达到 1,000 成功、零 errors/unknown；未重发
任何单个不确定 publish。两轮 raw 和诊断均保留。

共享主机上还有其他项目编译（独立 Redis/task boundary refactor、model
metadata、reflection、model 文档 fixture）；没有修改或终止外部进程。每次
invocation 记录 UTC、load、CPU ticks、端点观察的编译器；端点快照可能漏掉
中间出现的任务。早期使用未限时编译守候，恢复后的 driver 改为每 case 最多
30 秒、累计最多五分钟，预算耗尽后带扰动 flag 继续。一次获授权、fixture-free
的 focused test 暂停为 167.807298 秒，计入 guard wall-clock；恢复时保守
有效编译守候上界 224.831843 秒。暂停不计入任何业务计时，UTC 暂停/恢复与
原始预算记录保留。外部负载影响吞吐和尾延迟，表格是实测分布，不是跨机器
固定性能门槛。

### 有限复测与阶段 wall-time 分解

唯一一次 follow-up guard 等待 120.032572 秒后到期，未取得观察到的安静窗口。
全部 16 个 follow-up invocation 的起止端点均有编译器。八个 fresh standalone
工作轮（8,000 成功、零 errors/unknown）复核 sync concurrency 1：4,096 字节
三对、262,144 字节一对。主矩阵 sync 4,096 字节比值为 0.739/0.838/0.798
（中位数 0.798）；复测为 1.026/0.394/0.727（中位数 0.727）。大 payload
复测比值 0.666。它们保留了表观性能下降的问题，但波动及持续共享负载使
稳定退化无法归因到实现。

独立临时 phase driver 用相同公开 provider SPI、真实 before/after 路径，
预建 1,000 消息，用 `Instant` 分别计 publish、receive（3 秒接收调度预算）、
Accept。任何错误即停止，没有重放或补齐配额。八个 phase invocation 均
完成 1,000 成功、零 errors/unknown（合计 8,000）。两侧 phase main 源码
逐字节一致，lock 审查没有包版本/source 差异。诊断在主线程运行，没有
INFO observer/worker barrier；CSV 写入在事件之间且不计入各阶段计时。
阶段绝对总和不能替代主矩阵 worker-region 吞吐。这些是包含网络、调度和
执行的 wall-time 分解，不是 CPU flamegraph。

一个 before async 262,144 字节诊断在 Docker fixture startup 阻塞超过三分钟，
尚无业务样本，其他独立 Docker start 也在等待。仅确认自有的 Docker CLI 在
11:56:35.758088 UTC 收到 SIGTERM；启动请求恰在该边界完成，原 Rust 进程
继续完成全部 1,000 events，无错误或重试。after 诊断也正常完成，不能称
signal 修复了 Docker。fixture setup 排除于阶段计时，invocation 环境快照
包含该延迟。最终确认唯一自有 mount 已无对应 container；全部自有进程退出
后才释放计算窗口。

四对 phase 的 publish 均值都升高，receive/settle 则有双向变化，例如 sync
4,096 字节 receive 从 294.3 降至 254.4 µs，而 sync 262,144 字节从 9,421.8
升至 13,194.9 µs。它们不能证实某个 serializer/parser 就是根因。未来受控
CPU profile 的静态候选是 bounded writer 写检查/容量增长，以及 version
probe、结构深度检查、typed wire decode 的多次遍历。任何优化提案必须保留
version/error 优先级、ignored-field 深度与 duplicate selector 检查、inclusive
大小预算及 Redis I/O 前拒绝。此次没有实施这类生产优化，也没有根据带噪声
数据宣称其收益；稳定归因仍需要受控主机测量。

## 历史单轮实验

以下数据保留为历史，不能作为当前矩阵的 before 对照。

Docker `redis:7-alpine`、10 个同步 idle subscription、1,000 次顺序
publish/receive/accept；各轮新建 Redis 容器，`REDIS_BENCH_IDLE_SECONDS=30`。

```sh
REDIS_BENCH_IDLE_SECONDS=30 cargo test --test connection_reuse_benchmark_tests -- --ignored --nocapture
```

历史 before 为 `b6be1e7b9b203b8391f705ef83c043646e79bfa2`；after 为
`87e6eb013d5a3065df7cb3c2f44eb2a44b43697f` 加当时未提交的 receive 连接复用改动。

| 指标 | 历史 before | 历史 after |
| --- | ---: | ---: |
| idle consumer | 10 | 10 |
| idle 观察窗口 | 30.033 s | 30.008 s |
| idle 期间新建 Redis 连接 | 2,960 | 10 |
| 每秒新连接 | 98.56 | 0.33 |
| 顺序 round-trip | 1,000 | 1,000 |
| 吞吐 msg/s | 1,039.52 | 2,068.25 |
| p50 µs | 942 | 454 |
| p95 µs | 1,070 | 653 |

该单轮中 idle 新连接下降 99.66%，吞吐为原来的 1.99 倍，p50 下降 51.8%、
p95 下降 38.9%。这是单轮测量，仅反映方向，不能形成稳定延迟/吞吐边界。
idle 连接包括每个 subscription 首次建立的专用 reader，timeout 不反复重连。
